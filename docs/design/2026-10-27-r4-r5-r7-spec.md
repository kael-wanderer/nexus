# R4, R5 and R7: next-release scope

2026-10-27 · Evidence checked against cc5b5f7. This is a proposal; the owner decisions below are not approvals.

## R4 — file search

**Problem.** `FileSearchProvider` searches the user's home by display-name prefix and requests four times the file cap (Sources/NexusCore/Search/Providers.swift:95–120). Spotlight collection stops at that limit (Sources/NexusCore/Search/MetadataQueryRunner.swift:148–160), so filtering afterwards cannot recover useful candidates. The review's screenshot is historical evidence, not a fresh measurement. File results already show the parent path and offer opening the parent (Providers.swift:127–145); the row renders the subtitle and exposes it to accessibility (Sources/NexusUI/Search/SearchPaletteView.swift:154–163,181–184).

**Decision proposed.** Exclude the current user's `~/Library` itself and descendants while collecting file-query results, before the limit. Compare standardised path components, not string prefixes, so `~/Library Notes` remains searchable. Leave other locations alone: blanket developer-folder exclusions would hide useful work. Keep existing asynchronous 120 ms debounce and prefix search; preserve the existing app/window <50 ms test (Tests/NexusCoreTests/SearchIntegrationTests.swift:82–112). The mockup records the existing parent-path presentation; it does not propose a new control. Ten deterministic examples and a limit-boundary test use a fake runner; a real Spotlight check remains manual because indexing varies.

**Out of scope.** Configurable roots or an include-excluded switch, recency, fuzzy retrieval changes, new result UI, corpus process, percentage targets, telemetry and dependencies. Library files remain available through Finder/Spotlight.

**Owner decisions needed.** Proposed default: hide all of `~/Library`, with no override in this release. Is that acceptable, including intentionally saved documents there? Is the existing full parent path satisfactory, as illustrated, or should a later release offer a shorter label?

## R5 — release walkthrough

**Problem.** The verification log still calls out switcher, settings typing, now-playing and hardware checks (docs/verification.md:153–178, 204–218, 231–258, 280–290); old entries also include checks later passed, so the checklist distinguishes a new release run from historical evidence.

**Decision proposed.** One short manual checklist, with candidate identity, exact actions, expected results, pass/fail and a notes field. Record unavailable equipment as blocked, never as pass; repeat permissions checks after restoring grants. It includes physical focus, drag, displays, power and audio as well as outstanding verification. No CI or automation framework.

**Out of scope.** Automated device testing, bug fixes and claiming a release pass without executing the checklist.

**Owner decisions needed.** Proposed release gate: every applicable row passes; unavailable physical hardware is blocked and requires an explicit owner release decision. Is that gate appropriate?

## R7 — interaction ownership

**Problem.** SidebarViewModel is 1,569 lines, PanelController 1,067 and Composition 556. The drag implementation mixes preview, configuration, spring loading and row rebuilding (Sources/NexusUI/Sidebar/SidebarViewModel.swift:1041–1215); group capacity and mutation also live alongside it (:742–783). Length alone does not establish a defect.

**Decision proposed.** Skip extraction for this release. Moving only state would leave transitions split across owners; moving all commit, group and spring-load behaviour requires a wider interface and risks changing working interaction code without a demonstrated release defect. The manual interruption checks in R5 supply a release signal. Revisit a single drag-session extraction when a concrete drag fix needs it, with unchanged existing tests and deterministic disappearing-target, full-group and cancel sequences.

**Out of scope.** PanelController or Composition extraction, speculative protocols, behavioural changes, and an R7 implementation task.

**Owner decisions needed.** Is deferring the drag extraction until a concrete fix acceptable? If not, allocate time for its design and interruption tests before asking a low-tier implementation agent to execute it.
